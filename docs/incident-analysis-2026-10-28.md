# 构建器打开后服务器失联：2026-10-28 排查记录

初次排查通过用户现有 Edge 登录会话进入阿里云控制台，使用云助手执行只读诊断。之后经用户授权覆盖更新现有项目并进行线上复验，结果见末节。以下时间均为北京时间。用户确认故障后的重启是手动操作。

## 结论与证据边界

直接触发路径已经定位到 **项目 131（2D 模板）的服务端兼容预览构建**。这个项目两次进入 `build` 阶段后，都未正常完成，直到故障后手动重启，任务才在服务启动恢复时标记为失败。

资源耗尽是首要解释：业务机内存余量小，Vite 需要处理 Phaser，现有调度只限制任务数量，没有为构建进程组限制 CPU 或总内存。但是，现存日志没有记录到故障瞬间的内存峰值，也没有 OOM kill 记录，不能把“内核 OOM 已证实”作为结论。

## 资源与项目检查

- 标称规格为 2 vCPU / 2GiB；操作系统报告可用物理内存总量约 1677MiB。
- 排查时可用内存约 716MiB；已有 `/www/swap`，容量 1GiB，当前使用量为零。
- 同机还运行 MySQL、宝塔、另外一个 Next.js 服务和一个 Node 后端。排查时 MySQL RSS 约 192MiB，Agent 后端约 152MiB，Next.js 约 140MiB。
- 磁盘使用率约 53%，尚有约 18GiB 空间。
- `sysstat` 最后一个故障前常规采样在 08:30：CPU 空闲 98.69%，可用内存 704872KiB，Swap 未使用。
- PCP 性能归档结束于 08:36:14，早于触发构建的 08:36:31；该归档在结束前仍显示正常基线。不能用这些较早采样证明故障瞬间没有资源耗尽。
- 当前启动、上一次启动及再前一次启动的内核日志均未检索到 OOM kill 记录。应用日志在重启后只保留了本轮启动输出，缺少上轮构建的 stdout/stderr。
- 项目 131 的 `src` 仅约 16KiB，`App.vue` 约 7.8KiB，`public` 约 12KiB；存在 `import * as Phaser from 'phaser'`，依赖为 Phaser `^4.0.0`，构建脚本为 `vite build`。
- 当次项目 131 的快照列表接口响应仅 47 字节；快照全量返回虽是独立性能隐患，但不是本次主要证据。

## 对应代码

1. `gameAgent/src/builder/preview/PreviewPanel.vue`：打开项目即调用 `loadPreview()`；浏览器预览失败或已记住兼容模式时，启动服务器预览。
2. `gameAgent/src/builder/preview/useCompatiblePreview.ts`：兼容模式启动后调用 `controller.update()`，并按项目保存模式记忆。
3. `node/exec/build/pipeline.js`：在同一台业务服务器执行依赖安装、`pnpm run build` 和上传。失败任务最后阶段为 `build`，说明排查重点应在 Vite 构建而非上传。
4. `node/exec/build/environment.js`：默认 `--max-old-space-size=512` 是每个 Node 子进程的 V8 老生代堆限制，不是整个构建进程组的总内存上限。
5. `node/exec/build/scheduler.js`：单进程内串行运行一个任务，但未提供 CPU 限额、进程组总内存限额或低内存拒绝启动机制。

线上 `pipeline.js` 与 `service.js` 的 SHA-256 与本地版本一致。本地两个逻辑核的模板构建验证中，测试及构建进程总工作集峰值约 1GiB；这是 Windows 上复用依赖、模拟上传的测量，只能作为容量风险旁证，不能替代线上故障时刻的测量。

## 修复优先级

1. 取消“进入页面即自动在业务机生产构建”的行为；已有预览优先展示，新构建改为明确触发，避免打开该项目立即再次影响整机。
2. 将构建移到独立 worker，或为整个构建进程组设置可执行的 CPU、总内存与超时限制，给业务服务预留资源。只调整 V8 堆大小不足以完成隔离。
3. 针对 Phaser 的构建输入，在隔离环境中记录 Vite、pnpm、原生子进程的 RSS 和 CPU 峰值，再决定预打包、缓存或依赖处理优化。
4. 保留每个任务的阶段、子进程退出信号、stdout/stderr 和资源峰值，并保留重启前应用日志，以便区分 V8 内存不足、内核 OOM、Swap 抖动和原生构建进程异常。

初次只读排查阶段没有重新执行故障构建。浏览器诊断连接改为持续复用，减少新建连接造成的重复授权提示。

## 经授权实施的修复与线上复验

- 覆盖更新现有宝塔后端与前端站点，保留配置、数据库和项目文件。原始版本备份在 `/www/backup/agent-build-overlay-69754a134d9f`；后续策略调整前的备份在 `/www/backup/agent-build-overlay-5672c277552e`。
- 保留原 1GiB Swap 文件，新增约 3GiB 文件，总计约 4GiB，未在线执行 `swapoff`。
- 实测发现原 `vm.swappiness=0`。在 384MiB 回收阈值的受限构建中，Swap 峰值为 0，持续回收直至 300 秒超时。调整为 30 并持久化后，相同源码可以在同一资源预算内完成。这表明 Swap 策略是此次内存压力的重要配置因素；扩容文件本身不足以解决问题。
- 构建进程组统一限制为最多 1 核 CPU、640MiB 内存、768MiB Swap，从 384MiB 开始回收。持续低内存保护和独立系统超时继续生效。所有依赖仍完整打包，未对 Phaser 做删减或外部 CDN 替换。
- 相同源码失败后抑制自动重试，手动刷新仍可重试。预览和发布的产物缓存分开；缓存和诊断日志改用持久目录。
